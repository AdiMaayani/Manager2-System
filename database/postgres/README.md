# PostgreSQL Migration Target (Phase 2)

PostgreSQL DDL translated from the SQL Server baseline (`database/schema/tables.sql`) for the
service-refactor migration. Business logic is NOT reproduced as `plpgsql` functions here: under the
chosen strategy the logic that used to live in `database/SP/*.sql` moves into C# services/repositories,
so PostgreSQL only needs faithful schema (tables, constraints, indexes) plus data.

> Apply against a non-production database only. Local development uses the bundled Docker Compose
> stack (below), which applies these scripts automatically to a throwaway container on first start.

## Layout

```
database/postgres/
  README.md                 <- this file
  OBJECT_TRACKING.md         <- per-table translation status (source of truth for progress)
  docker-compose.yml         <- local Postgres 16; auto-applies schema/*.sql on first init
  schema/
    01_core_identity.sql     <- Employees, Roles, Departments, Users, UserRoles, UserDepartments, CompanySettings
    02_customers_sites_contacts.sql <- Customers, Sites, Contacts
    03_workitems_projects_quotes.sql <- Contractors, WorkItems, Project*, Quotes, assignments
    04_inventory_workreports.sql <- InventoryItems, WorkReports, report assignments/systems
    05_smartassignment.sql   <- Rec_* recommendation-engine tables
  validation/
    validate_schema.sql      <- asserts translated objects exist with expected shape
```

## Local development with Docker

A local Postgres instance backs the dual-run migration (shadow reads / dual writes). Dev-only
credentials: db `manager2_dev`, user `manager2`, password `manager2`.

```bash
# from database/postgres/
docker compose up -d          # start Postgres; schema/*.sql applied on first init
docker compose ps            # wait for "healthy"

# apply/verify schema on an already-initialized volume (or just to re-check):
docker exec -i manager2-postgres psql -U manager2 -d manager2_dev -f /docker-entrypoint-initdb.d/01_core_identity.sql
docker exec -i manager2-postgres psql -U manager2 -d manager2_dev < validation/validate_schema.sql

docker compose down          # stop, keep data
docker compose down -v       # stop and wipe (re-applies schema on next up)
```

The API reads the connection string from `ConnectionStrings:PostgresConnection`
(`Host=localhost;Port=5432;Database=manager2_dev;Username=manager2;Password=manager2`), set via
user-secrets for local dev. The Postgres provider stays inert until `DataProvider` flags are enabled
(`ShadowReadPostgres` / `DualWritePostgres` / `Primary`).

## Type mapping (SQL Server -> PostgreSQL)

| SQL Server | PostgreSQL | Notes |
|---|---|---|
| `int IDENTITY(1,1)` | `integer GENERATED BY DEFAULT AS IDENTITY` | BY DEFAULT (not ALWAYS) so data migration can insert explicit ids. |
| `bigint` | `bigint` | |
| `tinyint` | `smallint` | PostgreSQL has no tinyint; range enforced by CHECK where relevant. |
| `nvarchar(n)` | `varchar(n)` | PostgreSQL text is UTF-8; Hebrew stored natively. |
| `nvarchar(max)` | `text` | |
| `bit` | `boolean` | `((1))/((0))` defaults become `true/false`. |
| `datetime2(n)` | `timestamp(min(n,6))` | WITHOUT time zone. PostgreSQL caps fractional-second precision at 6, so `datetime2(7)` maps to `timestamp(6)` (100ns -> 1µs; negligible for this data). |
| `datetime` | `timestamp(3)` | Approximates SQL Server `datetime` precision. |
| `date` | `date` | |
| `decimal(p,s)` | `numeric(p,s)` | |
| `sysutcdatetime()` | `(now() at time zone 'utc')` | UTC default. |
| `sysdatetime()` / `getdate()` | `localtimestamp` | Preserves the (pre-existing) local-time default behavior for parity. |
| filtered unique index `WHERE (IsActive=1)` | partial unique index `WHERE ("IsActive" = true)` | |

## Identifier casing

Identifiers are kept in the original PascalCase using double quotes (e.g. `"CompanySettingsId"`).
This keeps column names identical to SQL Server so cross-provider payload parity comparison and
repository column-name constants stay shared. Always double-quote identifiers in queries against this schema.

## Timezone note

`timestamp` (without time zone) is deliberately chosen over `timestamptz` to preserve the existing
contract where the application stores and returns UTC values without offset. Changing to `timestamptz`
is a separate, explicitly-approved decision (it would shift semantics) and is out of scope for parity.
